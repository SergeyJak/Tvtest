# Tvtest: roadmap семейного IPTV-сервиса

**Статус:** план развития, не описание уже готовых функций.  
**Обновлено:** 2026-11-21.  
**Цель:** собственный круглосуточный IPTV-шлюз на VPS, доступный из нескольких домов, с отдельными безопасными подключениями, стабильными HLS-потоками и минимальной ручной поддержкой.

## Наши решения

- **Railway оставляем.** Не переносим существующие сайты, базы данных или приложения в рамках IPTV-проекта. Возможные переносы рассмотрим отдельно и постепенно.
- **Первое размещение: отдельный VPS в ЕС**, кандидат OVHcloud VPS-2 (4 vCore, 8 ГБ RAM). Перед оплатой проверяем условия хостинга, сетевой маршрут и достаточный трафик; тариф не считается окончательно выбранным.
- **Сначала надёжность одного канала, потом множество каналов и пользователей.** Локальный тест на Windows не равен готовому публично доступному сервису.
- **Пользователи:** Сергей, Кристина, родители. У домохозяйств уже есть собственные аккаунты Edem; по умолчанию каждому можно назначить свои учётные данные источника.
- **Один аккаунт Edem ≠ гарантированно одно устройство.** Один серверный IP не отменяет лимитов по одновременным потокам, аккаунтам и условиям использования подписки. Не строим архитектуру на предположении, что один ключ разрешает безлимитную трансляцию. Совместное использование одного источника включаем только там, где это допускает провайдер.
- **Одинаковые каналы и разрешённый общий источник → один upstream HLS fetch + общий кеш.** Если у зрителей отдельные подписки, ведём независимые сессии и кеши по `(source/account, channel, variant)`, не смешивая чужие токены.
- **Постоянный URL каждому зрителю**, HTTPS, возможность отозвать токен без смены чужих ссылок. Секреты никогда не коммитим.

## Исходная точка, что уже реализовано

Репозиторий содержит:
- `iptv_probe.py` и `iptv_continuous.py` для диагностики доставки сегментов.
- Одноканальный `iptv_gateway.py` (MPEG-TS HLS): буфер, ограниченный кеш RAM, автоопрос HLS, обновление источника после `MANIFEST_HTTP_404`, опциональное обновление приватного M3U через переменную окружения.
- Постоянный локальный токен шлюза (`.iptv_gateway_token`) и диагностику клиентских запросов (`client_manifest_200`, `client_segment_200`, `client_auth_404`).
- Подтверждённый короткий просмотр правильного токенизированного URL: около 20 минут без сбоев, но **долговременная стабильность ещё не доказана**.

Ограничения: один канал на экземпляр, начальная задержка (например, 90 секунд), отсутствие каталога/авторизации отдельных пользователей, нет серверного деплоя и автоматического перезапуска. Длительные upstream 404 не устраняются одним только буфером.

## P0: подтвердить стабильность текущего шлюза

- [ ] Провести просмотр одного канала минимум 2 часа, затем несколько вечеров, **через правильный URL** на ТВ.
- [ ] Зафиксировать воспроизводимые показатели: upstream 404, `upstream_stalled`, реальная глубина кеша, `client_manifest_503`, `client_segment_404`, успешные запросы клиентских сегментов.
- [ ] Записать сценарии: сеть пропала на 15/60/120 секунд, исходный URL вернул 404, пропущен сегмент, ТВ перезапущен, сменился upstream sequence.
- [ ] Убедиться, что gateway умеет работать длительно без роста памяти и с восстановлением после коротких перебоев. Отдельно изучить, как на поведение влияет большой кеш и `--delay`.
- [ ] Сравнить Edem напрямую и через шлюз на том же устройстве; не считать ошибку Edem исправленной без проверки.
- [ ] Тесты и CI на регрессию HLS, 404/503, Range 206 и авторизацию.

**Готово, когда:** непрерывный тест не теряет воспроизведение при кратких ожидаемых сбоях; любая остановка имеет понятную причину по метрикам. Длинный недоступный upstream честно отражается как outage.

## P1: один канал на VPS, доступ из другого дома

- [ ] Проверить у VPS-провайдера, разрешены ли личные IPTV-relay и соответствующий трафик; проверить лимиты, цену продления, географию дата-центра.
- [ ] Проверить у Edem условия доступа, разрешённое число потоков и использование сервера/VPS; для теста использовать собственный действующий аккаунт.
- [ ] Развернуть Ubuntu LTS, Docker Compose и Caddy (или аналог) с HTTPS; автозапуск после reboot, `restart: unless-stopped`, healthcheck.
- [ ] Ограничить доступ: firewall, SSH-ключи, закрыть прямой порт шлюза, публично оставить только HTTPS. Отдельный непубличный admin/status endpoint.
- [ ] Хранить M3U-адреса и секреты в защищённых переменных/файлах на VPS, а не в GitHub и не в логах.
- [ ] DNS-имя для сервиса, постоянный HTTPS URL. Переподключать телевизор при каждом деплое нельзя.
- [ ] Замерить маршрут **Edem → VPS → TV в Риге**: latency, 404, скорость и непрерывность минимум за сутки.
- [ ] Проработать вопрос подписки/сетевой доступности, если Edem ограничивает использование дата-центровых IP.

**Готово, когда:** один канал доступен извне по HTTPS, стартует после reboot и автоматически восстанавливается после перезапуска процесса, не требуя ручного запуска PowerShell.

## P2: общий каталог и несколько каналов

- [ ] Ввести `SourceManager`: несколько Edem-аккаунтов/плейлистов, отдельные креденшелы и политика доступа.
- [ ] Ввести `ChannelCatalog`: обновление M3U, стабильные channel IDs, название/группы/логотипы, фильтры и порядок, без раскрытия upstream URLs.
- [ ] Ввести `StreamManager`: запускать upstream только при первом зрителе, останавливать после таймаута без зрителей.
- [ ] Реализовать дедупликацию **только в рамках одной разрешённой source/account + channel + variant**. Разные аккаунты не склеивать автоматически.
- [ ] Буфер для активных каналов + небольшая предзагрузка избранных по настройке. Компромисс: холодный канал нельзя запустить с полными 90 сек буфера мгновенно.
- [ ] Обрабатывать переключение каналов, HLS sequence rollover/restart, независимые курсоры клиентов, лимиты RAM/CPU/network и защиту от множества одновременных активных каналов.
- [ ] Поддержать M3U `/user/{token}/channels.m3u`, устойчивые URL каналов и EPG (если доступен и разрешён).
- [ ] Проверить совместимость на Samsung, LG, Android TV и телефоне.

**Готово, когда:** семья переключает каналы из одного плейлиста без PowerShell; один разрешённый upstream-канал не скачивается повторно на каждого зрителя.

## P3: семейные аккаунты и управление

- [ ] Отдельные профили и ключи: Сергей, Кристина, родители. Ни один пользователь не видит URL/ключ источника или ключи остальных.
- [ ] Возможность привязать каждому профилю **свой аккаунт Edem** (предпочтительно, поскольку аккаунты уже есть).
- [ ] Опциональное совместное использование одной подписки/кеша **только если разрешено условиями провайдера**; контролировать не только IP, но и количество активных upstream-сеансов.
- [ ] Самообслуживание: выдача ссылки, ротация/отзыв ключа, список активных устройств, необязательные лимиты сессий.
- [ ] Админ-панель: активные каналы/зрители, ошибки upstream, клиентские 404/503, расход трафика, использование памяти и живость сервиса.
- [ ] Безопасность: HTTPS, rate limiting, токены достаточной энтропии, конфиденциальные логи, без публичного `/status`, firewall.
- [ ] Уведомление о длительном отказе источника, автоматический restart на падении процесса, резервная копия конфигурации/секретов с проверкой восстановления.

**Готово, когда:** можно выдать Кристине и родителям отдельные работающие ссылки и при необходимости отключить только одного пользователя, не затрагивая остальных.

## P4: оптимизация и эксплуатация

- [ ] Следить за потреблением CPU/RAM/SSD и outbound network, с предупреждениями до лимита трафика и fair use.
- [ ] Измерить частоту переключения каналов и подобрать `delay` для медленных/быстрых каналов отдельно.
- [ ] Вести небольшой dashboard и историю сбоев без чувствительных данных; healthcheck и простые smoke-тесты после деплоя.
- [ ] Автоматизировать развёртывание из GitHub (CI → Docker image → VPS), rollback и безопасные обновления.
- [ ] Документировать восстановление после падения VPS и ротацию ключей.
- [ ] **Только отдельным решением** рассматривать постепенный перенос некритичных приложений с Railway на тот же VPS. Сначала бэкапы, потом нагрузочные тесты и разделение ресурсов. Текущие Railway-сервисы не трогаем.

## Минимальная архитектура (целевая)

```text
Сергей (свой токен) ------\
Кристина (свой токен) -----+--> HTTPS / Caddy --> Auth + Catalog --> StreamManager
Родители (свой токен) ----/                                    |
                                                          HLS cache
                                                               |
                                            SourceManager / permitted account(s)
                                                               |
                                                        Edem / iLook
```

Для **одного разрешённого account+channel** несколько зрителей получают копии из одного кеша. Для **разных каналов** нужны разные upstream-потоки. Для **разных подписок** держим независимые обращения к источнику. Трафик **VPS → каждый зритель** остаётся отдельным даже при общем кеше, поэтому расходы зависят от числа зрителей и времени просмотра.

## Что не делаем сейчас

- Не переносим Railway проекты.
- Не покупаем несколько VPS и не строим панель, пока не подтверждён удалённый просмотр одного канала.
- Не сохраняем M3U/ключи Edem/токены пользователей в репозитории, PR и CI logs.
- Не обещаем безотказность при upstream 404 или разрешённость общего ключа на несколько домохозяйств.
- Не выдаём публичные IPTV URL без HTTPS и авторизации.
